# 3D模型节点轮询优化与模型加载修复设计方案

## 1. 背景与问题概述

### 1.1 问题一：3D模型节点轮询导致蓝图页面卡顿

在AI工作流蓝图页面中，Meshy与Tripo3D两种3D模型节点在执行任务期间，采用固定频率的setInterval轮询机制查询后端任务状态，导致整个蓝图页面出现明显卡顿，表现为：

- 画布节点拖拽延迟、掉帧
- 节点连线渲染不流畅
- 面板操作（如属性面板、任务面板）响应迟缓
- 严重时浏览器标签页出现无响应提示

### 1.2 问题二：Meshy任务完成后3D模型加载报JSON解析错误

Meshy任务成功完成后，点击"打开3D编辑器"按钮时，3D编辑器页面抛出如下错误：

```
Model3DEditorPage.vue:688 [Model3DEditor] Failed to load model:
SyntaxError: Unexpected token '�', "�PNG，" is not valid JSON at position 0
```

导致3D模型无法在编辑器中渲染。

### 2.1 项目架构回顾

根据 `AGENT_GUIDE.md`，项目采用**图形底座 + 蓝图业务层**双层架构：

```
┌──────────────────────────────────────────────────────┐

│   - Vuex管理：页面级UI状态 + 引擎状态只读投影          │
│   - 命令栈 / IPC通信封装                              │
├──────────────────────────────────────────────────────┤
│  图形底座 (Canvas / WebGL / Pixi.js)                  │
│   - 2D渲染场景图 / 节点与连线绘制                      │
│   - 鼠标/键盘交互 / 拖拽缩放                          │
│   - 引擎内部管理蓝图绘制状态（唯一权威数据源）         │
├──────────────────────────────────────────────────────┤
│  Electron主进程 (Node.js)                             │
│   - HTTP客户端 (http-client.mjs)                      │
│   - 各AI服务模块 (meshy/service.mjs 等)               │

└──────────────────────────────────────────────────────┘
```

**事件通信链路**：前端渲染进程 → `window.dweb.*` IPC调用 → Electron主进程 → 后端模块 → 第三方API（Meshy/Tripo3D），返回路径相反。

### 2.2 轮询卡顿根因分析

#### 2.2.1 当前轮询实现位置

| 节点类型 | 文件位置                                                                    | 轮询入口函数                           | 当前间隔   |
| -------- | --------------------------------------------------------------------------- | -------------------------------------- | ---------- |
| Meshy    | `src/views/AIWorkflow/node-business/meshy/useAIWorkflowMeshyRuntime.ts`     | `startMeshyPoll(nodeId, taskId, mode)` | **1600ms** |
| Tripo3D  | `src/views/AIWorkflow/node-business/tripo3d/useAIWorkflowTripo3DRuntime.ts` | `startTripo3DPoll(nodeId, taskId)`     | **2000ms** |

#### 2.2.2 当前轮询代码模式（以Meshy为例）

```typescript
const startMeshyPoll = (nodeId: string, taskId: string, mode: string) => {
	stopMeshyPoll(nodeId)
	// 立即执行一次，然后每1600ms固定间隔
	void tick()
	const timer = window.setInterval(() => void tick(), 1600)
	meshyPollTimers.set(nodeId, timer)
}

const tick = async () => {
	// 1. 检查节点状态，若终态则stop
	// 2. IPC调用 comfySvc.meshyTask(taskId, mode) 查状态
	// 3. 调用 applyMeshyTaskResult() 处理结果
	//    - 内含大量 store.commit() 更新节点设置
	//    - 下载外部资源、更新进度、同步下游节点
	//    - 刷新任务列表 UI
}
```

#### 2.2.3 卡顿的6层根因

| 层级                             | 根因                                                                              | 影响说明                                                 |
| -------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **#1 固定高频轮询**              | Meshy 1.6s / Tripo3D 2s，无法根据任务状态动态降频                                 | 任务执行可能持续5~30分钟，全周期高频请求无意义           |
| **#2 多节点并行放大**            | 每个节点独立 timer，N 个节点并行 = N 倍请求量                                     | 3个Meshy节点时 = 每秒约1.875次请求 + 响应处理            |
| **#3 每次轮询触发Vue响应式风暴** | `applyMeshyTaskResult()` 内部调用 `store.commit()` 更新 `nodesById`               | Vuex state变更触发蓝图所有节点组件的 computed/watch 重算 |
| **#4 轮询回调内重度工作**        | 每次 tick 除了查状态，还执行：资源持久化下载、进度条更新、刷新任务列表、Toast推送 | 主线程被大量 I/O 和 DOM 更新阻塞                         |
| **#5 终态清理不彻底**            | 仅在 `tick()` 内部判断终态才 stop；节点被删除 / 页面关闭时的清理未覆盖所有路径    | 定时器泄漏导致无效轮询继续占用主线程                     |
| **#6 进度回调过于密集**          | 下载进度每帧更新 → 每帧触发 Vuex commit → 每帧重渲染 UI                           | 下载 10MB 文件可能触发上千次重渲染                       |

### 2.3 PNG-JSON解析错误根因分析

#### 2.3.1 完整调用链路

```
[workflow节点] WorkflowModel3DNode.vue:L1290-L1302
  └─ onOpenEditor()
       └─ effectiveModelUrl (computed L529-L537)
            ├─ settings.modelAssetUrl  (优先，本地持久化URL)
            └─ settings.modelUrl       (回退，原始URL)
                 └─ (若为meshy.ai远程URL则被 isRemoteMeshyUrl 过滤为非优先)

[composable] useModel3DEditor.ts:L20-L52
  └─ open() → open3DEditor(models=[{url, id, name}])
       └─ Electron IPC → 新窗口加载 Model3DEditorPage + hash?models=JSON(...)

[3D编辑器] Model3DEditorPage.vue:L618-L692
  └─ initEditor()
       ├─ parseModelsFromQuery() → JSON.parse 解析模型元数据（正确）
       └─ viewer.loadModel(m.url)  ← 问题发生在这里
            └─ EditorViewer.ts:L1171-L1195 loadModelFile()
                 ├─ 取扩展名 (.png / .glb / .obj 等)
                 ├─ 非.obj → 默认走 GLTFLoader.load()
                 └─ GLTFLoader 内部 fetch URL → 尝试 JSON.parse()
                      └─ 若 URL 实际是 PNG 图片 → 抛出错误："�PNG is not valid JSON"
```

#### 2.3.2 罪魁祸首：Meshy后端的错误fallback

定位文件：`electron/backend/modules/meshy/service.mjs` → `normalizeTask()` → 第239-281行

```javascript
const imageUrls = allFoundUrls.length > 0 ? allFoundUrls : ...
const preferredImageUrl = imageUrls.length > 0 ? imageUrls[0] : ''
const primaryRemoteUrl = preferredModelUrl || preferredImageUrl   // ⚠️ 关键BUG

return {
  ...
  preferredModelUrl: primaryRemoteUrl,   // 当 modelUrls 为空时，
  sourceModelUrl: primaryRemoteUrl,      // modelURL 居然回退成了图片URL！
  ...
}
```

当 Meshy API 返回的 `model_urls` 为空（例如任务还没完全生成好3D文件、或API返回结构异常），`preferredModelUrl` 会被错误地填充为缩略图图片URL。再经过前端`useAIWorkflowMeshyRuntime.ts` 的 `applyMeshyTaskResult()` → `pickMeshyPreferredModelUrl(modelUrls)` 链路，最终将图片URL写入到 `model3dSettings.modelUrl`。

#### 2.3.3 触发条件（3种场景）

| 场景      | 原因                                                                                     |
| --------- | ---------------------------------------------------------------------------------------- |
| **场景A** | Meshy任务刚变成succeeded状态时立即下载，model_urls还未就绪 → 图片URL被fallback为modelUrl |
| **场景B** | Meshy API接口版本变更或返回字段缺失 → model_urls为空 → fallback                          |
| **场景C** | 本地资源下载失败 → catch分支回退使用远端URL → 仍是图片URL                                |

结果：`effectiveModelUrl` = `https://...meshy.ai/.../thumbnail.png` → GLTFLoader尝试JSON.parse → 看到首字节是PNG魔数 → 报错。

### 3.2 方案一：统一任务轮询调度中心（解决轮询卡顿）

#### 3.2.1 架构设计

```
┌──────────────────────────────────────────────────────────────────┐
│                 Task Poll Scheduler (单例)                       │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │  调度队列 Map<nodeId, PollTask>                            │  │
│  │    - taskId, provider (meshy|tripo3d), mode, status       │  │
│  │    - 创建时间, 上次轮询时间, 已运行秒数                     │  │
│  │    - 动态间隔策略 (指数退避 + 状态感知)                     │  │
│  └────────────────────────────────────────────────────────────┘  │
│                            ▲                                     │
│                            │ 单次 tick (rAF驱动，与渲染帧对齐)    │
│                            │                                     │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │  结果节流器 (StateUpdateBatcher)                           │  │
│  │    - 100ms 窗口批量收集 poll result                         │  │
│  │    - 窗口结束一次性合并 commit 到 Vuex Store               │  │
│  │    - 进度更新按帧节流 (最多每帧1次)                          │  │
│  └────────────────────────────────────────────────────────────┘  │
│                            ▲                                     │
└────────────────────────────┼─────────────────────────────────────┘
                             │ register / unregister
              ┌──────────────┴──────────────┐
              ▼                             ▼
    MeshyRuntime (接入调度器)        Tripo3DRuntime (接入调度器)
```

#### 3.2.2 动态间隔策略（核心）

替换固定1600ms/2000ms为**任务年龄感知 + 状态感知 + 指数退避**混合策略：

```
间隔(任务状态, 任务已运行秒数, 连续错误数, 窗口可见性) =

  // 阶段1：任务前60秒，相对高频（用户等待反馈）
  if age_seconds < 60:
    2000ms + random(0~400ms)    // 基础2s，抖动避免惊群

  // 阶段2：60~300秒，逐步降频
  else if age_seconds < 300:
    4000ms + random(0~800ms)    // 4s基础

  // 阶段3：超过5分钟，低频轮询
  else:
    8000ms + random(0~1600ms)   // 8s基础，最多每8s查一次

  // 状态感知：progress有变化时短期升频
  if last_progress_changed_within_30s:
    interval *= 0.6

  // 连续错误退避
  interval *= (1.5 ^ consecutive_errors)  // 1错误→1.5x，2错误→2.25x...

  // 窗口不可见(页面tab隐藏)时 ×2
  if document.hidden:
    interval *= 2

  // 安全边界：min=1.5s，max=30s
  clamp(interval, 1500ms, 30000ms)
```

#### 3.2.3 批量提交与帧节流策略

```
当前(每轮)：
  tick1 → applyResult → store.commit → Vue重渲染
  tick2 → applyResult → store.commit → Vue重渲染  (卡顿源)
  tick3 → ...

优化后：
  ┌─ 100ms 收集窗口 ────────────────────────────┐
  │ tick1.result → pending                        │
  │ tick2.result → pending (若同节点则覆盖合并)   │
  └──────────────────────────────────────────────┘
           ↓
       rAF回调时机执行：合并结果 → 单次 store.commit → 单次 Vue 更新
```

**额外规则**：

- 进度条（progress）更新最多每帧(16ms)1次
- Toast通知、下载开始/完成这种非频繁事件直接透传
- 终态（succeeded/failed/canceled）立即透传不等待窗口

```

  │   ├── TaskPollScheduler.ts      (核心：单例调度中心)

修改：
```

#### 3.2.5 生命周期与清理保障（防泄漏）

```
清理触发点：
  ✓ 节点终态（succeeded/failed/canceled） → scheduler 内部 auto unregister
  ✓ 节点被删除（store mutation removeNode）→ 订阅删除事件 → unregister

```

### 3.3 方案二：Meshy 3D模型URL校验 + 加载器防护（解决PNG-JSON错误）

#### 3.3.1 多层防御设计

采用**5层纵深防御**，每一层独立都能拦截问题：

```
Layer 1: 后端输出校验（根本解决）
  electron/backend/modules/meshy/service.mjs
    normalizeTask() 禁止 preferredModelUrl fallback 到 imageUrl

Layer 2: 前端结果消费校验（入口拦截）
  useAIWorkflowMeshyRuntime.ts applyMeshyTaskResult()
    pickMeshyPreferredModelUrl() 若返回图片扩展名 → 视为空 + 记录warn

Layer 3: 节点 effectiveModelUrl 计算层（渲染前拦截）
  WorkflowModel3DNode.vue effectiveModelUrl computed
    增加扩展名白名单检查，拒绝 .png/.jpg/.jpeg/.gif/.webp/.bmp/.svg 作模型URL

Layer 4: EditorViewer 加载器（最后技术防线）
  EditorViewer.ts:loadModelFile()
    扩展名嗅探 + fetch 后 Content-Type/Magic Number 检查
    发现非3D文件 → reject 友好错误信息，不触发 JSON.parse

Layer 5: 错误提示 UI（用户体验保障）
  WorkflowModel3DNode.vue / Model3DEditorPage.vue
```

#### 3.3.3 Layer4 EditorViewer加载器防护改动内容

文件：`src/ui/WorkFlow/WorlFlowNodes/model3d/editor/EditorViewer.ts`

```typescript
// 新增：3D模型扩展名白名单
const MODEL_EXT_WHITELIST = new Set([
  'glb', 'gltf', 'obj', 'fbx', 'stl', 'dae', 'usdz', '3ds', 'ply'
])
const IMAGE_EXT_BLACKLIST = new Set([
  'png', 'jpg', 'jpeg', 'gif', 'webp', 'bmp', 'svg', 'tif', 'tiff'
])

// 修改 loadModelFile(url):
private async loadModelFile(url: string, onProgress?): Promise<any> {
  // Step 1: 扩展名预检
  const ext = url.split('.').pop()?.toLowerCase().split('?')[0] || ''
  if (IMAGE_EXT_BLACKLIST.has(ext)) {
    throw new Error(`[ModelLoader] URL appears to be an IMAGE (.${ext}), not a 3D model. ` +
      `Please check the model source URL. Raw url: ${this.sanitizeUrlForLog(url)}`)
  }

  // Step 2: GLTFLoader路径 - 增加响应类型校验
  if (ext !== 'obj' || !this.objLoader.load) {
    // GLTFLoader的内部路径：新增before-load钩子验证响应
    // 或用自定义 fetch + 响应头检查 → 再交给 loader.parse
    // GLTF格式规范：响应要么是 binary (.glb, magic "glTF") 要么是 JSON (.gltf)
    return this.loadGltfWithValidation(url, onProgress)
  }
  // ... OBJLoader 路径保持不变
}

// 新增：loadGltfWithValidation - 检查 magic number 再解析
private async loadGltfWithValidation(url, onProgress) {
  const resp = await fetch(url)
  if (!resp.ok) throw new Error(`HTTP ${resp.status}: ${resp.statusText}`)
  const contentType = resp.headers.get('content-type') || ''
  const isImage = /^image\//.test(contentType)
  if (isImage) {
    throw new Error('[ModelLoader] Server returned image/* content-type for model URL. ' +
      'This usually means the model generation did not complete or the URL is a thumbnail.')
  }
  const buffer = await resp.arrayBuffer()
  // GLB magic number: 字节0..3 = 0x676C5446 ("glTF" little-endian)
  const view = new DataView(buffer)
  const isBinaryGLB = buffer.byteLength >= 4 && view.getUint32(0, true) === 0x676C5446
  if (!isBinaryGLB && ext === 'glb') {
    // 非GLB二进制，尝试JSON解析前检查首字符
    const firstByte = view.getUint8(0)
    // JSON以 '{' 或 '[' 开头
    if (firstByte !== 0x7B && firstByte !== 0x5B) {
      const firstBytesStr = String.fromCharCode(firstByte, view.getUint8(1), view.getUint8(2), view.getUint8(3))
      throw new Error(`[ModelLoader] GLB/GLTF content validation failed. First bytes: "${firstBytesStr}". ` +
        `Not a valid 3D model file (expected JSON or glTF binary magic).`)
    }
  }
  // 校验通过，交给GLTFLoader.parse
  return new Promise((resolve, reject) => {
    this.gltfLoader.parse(buffer, '', (gltf) => resolve(gltf.scene), reject)
  })
}
```

## 5. 非破坏性保障：不影响现有Electron功能

### 5.1 修改原则

1. **新增而非替换**：`TaskPollScheduler` 作为独立模块存在，原 `startMeshyPoll`/`startTripo3DPoll` 函数签名100%保留，内部改为调用调度器；若调度器初始化失败，自动fallback回原setInterval逻辑。
2. **修改文件最小化**：
   - 后端仅修改 `service.mjs` 中的 `normalizeTask()` 函数内部赋值（局部变量级别改动），不影响任何已存在的IPC handler路由。
   - 前端现有Vue组件的props、emit、computed名称完全不变。仅在computed内部增加额外if分支做防御性检查。
3. **Electron打包零破坏**：所有新增 `.ts` 文件位于 `src/views/AIWorkflow` 目录下，属于渲染进程代码，已经在现有 Vite/Webpack 打包范围内，无需修改 electron-builder 配置（`package.json`/`electron-builder.yml`）。
4. **主进程零改动**：主进程（`electron/main`）、Preload脚本、IPC channel 名称/契约均未修改，完全规避影响electron核心启动逻辑的风险。

### 5.2 风险与Feature Flag

为绝对安全，**可选择**新增一个全局开关：

```typescript
// src/config/feature-flags.ts (如已有类似则复用，没有则无需新建，直接启用)
export const FEATURE_FLAGS = {
	TASK_POLL_SCHEDULER: true, // 可通过 localStorage 临时关掉做回滚
	MODEL_URL_VALIDATION: true // URL校验开关
}
```

线上发现异常时，在控制台执行：

```js
localStorage.setItem('dv:disablePollScheduler', '1')
location.reload()
```

即可恢复旧行为。
